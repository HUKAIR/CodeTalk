# 可核验记录与模型推断

CodeTalk 区分原始工程记录和模型生成的解释。记录可以追溯到对应来源；
模型解释用于辅助阅读，仍可能遗漏或误解决定。可追溯性本身不证明记录正确、
完整或仍然适用。

本文只使用合成示例，不包含访谈原文、个人信任评分、真实会话或使用记录。

## 合成对照

假设一个示例项目记录了以下决定：

> Vibe-Decision: 保留按提交标识缓存的叙事；同一提交的原始内容不会变化。
> Vibe-Rejected: 每次修改配置就清空全部历史缓存；会增加重复计算。

随后，一个合成改动准备在配置变化时清空历史缓存。

| 材料 | 能提供的依据 | 限制 |
| --- | --- | --- |
| 当前 diff | 哪些分支和调用发生变化 | 不一定包含此前拒绝某种方案的原因 |
| 原始决定记录 | 当时明确写下的选择与否决理由 | 需要核对出处、适用范围和是否已被后续决定取代 |
| 模型解释 | 对已有材料的整理与可能解释 | 不是新增事实，也不能替代原始记录 |
| 人工判断 | 本次改动是否与仍有效的决定冲突 | 必须与机器呈现的证据分开记录 |

示例中的文字是人为编写的测试材料，不表示产品已阻止真实事故。

## 如何自行核对

在使用者自己的本地仓库中，可以用 `blame`、`search` 或 `review` 定位证据，
再通过 `git show <COMMIT>` 阅读对应记录。提交标识只用于定位内容，
不表示内容已被审核或批准。

可选的盲测脚本 `scripts/blind_test.py` 会调用模型。运行前须理解读取范围、
脱敏方式和远端目的地；不要为了公开演示上传真实用户会话或私有代码。

## 对外说明的边界

- 用公开合成 fixture 演示查证流程，避免复用真实用户资料。
- 不把单次示例、作者自测或模型评价当作用户研究结论。
- 不宣称已有证据证明信任提升、返工减少或事故被阻止，除非有对应授权和验证。
- 历史材料可能不完整；没有找到记录时，应明确说明缺口。
